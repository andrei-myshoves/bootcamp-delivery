# AGENTS.md

Общие правила разработки `bootcamp-delivery` для людей и AI-агентов. Правила собраны из договорённостей команды и замечаний code review; при появлении новой договорённости дополняйте этот файл.

Стек: React 19, TypeScript, Vite, TanStack Router (файловые маршруты), MobX, Tailwind CSS 4, i18next, ky, Storybook, Vitest, Playwright.

## React и компоненты

- Не выносить дочерний компонент только ради JSX. Если разметка используется в одном месте, не содержит своих хуков и логики и не даёт отдельной переиспользуемой функциональности — она остаётся в странице или родительском компоненте. Отдельный компонент оправдан, когда он переиспользуется или имеет собственную ответственность.
- Не усложнять архитектуру без необходимости: не добавлять слои, обёртки и абстракции «на будущее».
- Тесты и Storybook stories можно писать прямо для страниц, в том числе для разных состояний.
- Использовать существующие компоненты проекта и их значения по умолчанию. Например, у `Button` вариант `primary` задан по умолчанию — `variant="primary"` явно не указывать.
- Страница не должна показывать пустой экран, если для неё нет данных: перенаправлять на существующий маршрут (через `beforeLoad` маршрута и/или `<Navigate>`), не создавая новых маршрутов и искусственных данных.
- Пользовательский текст — только через i18n (`src/app/i18n.ts`), без строковых литералов в JSX.

## TypeScript и функции

- Не использовать `any`.
- Передавать функциям только необходимые данные, а не весь объект store (`this`). Тип входного объекта описывает ровно используемые поля; не изображать ограничение через `Pick` от store, если фактически передаётся весь store.
- Явно описывать типы входных и выходных данных функций и API (DTO, ответы, ошибки).
- `null` и `undefined`: отсутствие значения, которое возвращаем или записываем сами, — `null`. `undefined` вручную не возвращать; его оставляем там, где его порождает сам JavaScript (необязательные поля, optional chaining).

## Store и организация файлов

- Связанные файлы одного store, когда их несколько и у них общая ответственность, группировать в директории с именем store. Пример: `src/store/DeliveryCalculatorStore/` — создание заказа (`createOrderDto`, `orderSubmitError`, тесты `submitOrder`).
- Не смешивать тесты и логику разных store.
- Называть файлы последовательно и по смыслу; не добавлять суффиксы вроде `.order`, когда других файлов такого вида нет.

## UI и Figma

- Figma — источник истины для внешнего вида. Desktop и Mobile сверять отдельно: Mobile — самостоятельная композиция, а не уменьшенный Desktop.
- Для иконок проверять исходный SVG: `width`/`height`, `viewBox`, прозрачные поля и то, из какого фрейма сделан экспорт. Не подгонять размер иконки произвольными `width`/`height`, если причина может быть в экспорте.
- Использовать существующие дизайн-компоненты и токены; глобальные токены не менять ради одного места.
- Изменение UI-компонента включает stories и скриншот-тесты. Эталоны скриншотов генерировать только в Docker (`npm run test:visual`), просматривать каждый новый эталон и не обновлять существующие эталоны вслепую.

## Git и качество

- Ветка — от `dev`, имя — английское название задачи YouGile в kebab-case. Коммиты — Conventional Commits. PR — в `dev`, заголовок `<BOO-ID>: <English title>`, описание — только ссылка на задачу YouGile.
- Не выполнять commit, push, force push, merge, создание или изменение PR без явного разрешения.
- Перед завершением задачи запускать проверки и сообщать их фактический результат:
    - `npm run format:check`
    - `npm run lint` и `npm run lint:css`
    - `npm test -- --run` (локально на Node 25 — с `NODE_OPTIONS=--no-experimental-webstorage`)
    - `npm run test:e2e`
    - `npm run build`
    - `npm run test:visual` — для изменений UI
- Не создавать реальные заказы в Backend из тестов: запросы к API в тестах подменяются.
